# 杀戮尖塔 1 基础知识库：资料源与设计建议

> 后续执行以[基础知识库建设执行计划](基础知识库建设执行计划.md)为准。用户已指定小黑盒 Wiki 与英文 wiki.gg 为双主源；本文保留早期调研记录，灰机仅作补充来源，不再作为主中文源。

调研日期：2026-09-17。本文记录实际访问核查结果与建议。P1 纵向样本已经建立在 `data/spire.sqlite`，全量采集仍未完成。

## 当前方向

先建立游戏事实与机制资料。当前基础库只整理用户指定的中英文 Wiki，暂不把《端口化入门攻略》《胜利的方程式》关联到实体；两份攻略保持独立，未来如需策略层再另行设计。当前阶段采用文档学习；旧设计中“视频为准、文字仅校对”的要求已不符合用户当前方向。

不建立向量索引，不将材料切块做相似度召回。采用稳定实体 ID、名称与别名查找、结构化筛选、全文关键词搜索和显式关系导航。Agent 按问题读取条目及其关联页面。

本次浏览还发现：网页纯文本提取会漏掉以图标表达的能量数量，例如“获得能量”可能只剩下“Gain .”。因此不能只抓正文文本就生成结构化数值；须读取模板/结构化字段、图标语义或与游戏数据核对。本轮已探测 wiki.gg MediaWiki API 并保存 Body Slam JSON 样例；小黑盒公开批量 API 尚未确认，完整动态目录仍需浏览器或站点实际接口。

## 来源保存

每条事实或解释保留来源 URL、页面标题、修订号（可获得时）、采集时间、语言、适用游戏版本、核对状态。

wiki.gg 页脚标注 CC BY-SA 4.0，灰机首页标注 CC BY-NC-SA 4.0。保留各自署名与许可信息；页面文本和游戏图片分别记录来源，不假定图片与文本授权完全相同。

游戏本地版本的数据导出是后续优先核对依据，尤其适合内部 ID、基础属性、升级值、原始中英文描述。项目旧方案已提出 SpirePatch dump，但本次检查未发现已实现的数据导出产物，不能把计划视作现成能力。敌人 AI 和复杂事件条件也未必能由简单字段 dump 完整获得，需要专项提取或机制校验。

## 存储建议：SQLite 主库与可生成的 Wiki 页面

数据库保存可查询的事实与关系，Markdown 页面提供可读、可互链的说明。两者不是两份人工独立维护的全量数据：事实字段由数据库生成页面。两份攻略保留为独立 Markdown，当前不通过实体 ID 关联。

选择 SQLite 的原因：本地单文件、可用 Python 标准库直接操作，方便筛选、约束和备份。当前规模不需要独立数据库服务或图数据库。显式关系表已经能支持关联和反向链接。

建议的数据分层：

| 层 | 内容 | 管理方式 |
| --- | --- | --- |
| 原始资料 | 原始 Wiki 页面/数据快照、游戏导出 | 不覆盖来源，保留时间、版本和校验信息；两份攻略不属于当前基础库采集范围 |
| 游戏事实 | 角色、卡牌、遗物、药水、敌人、事件、关键词、规则 | 分类结构化表，与来源关联 |
| 机制解释 | 触发时机、结算顺序、叠加规则、特殊交互 | 可读说明及结构化条件；区分核实与待核实 |
| 策略认知 | 选牌、升级、搭配、路线、对敌策略 | 作为未来独立策略层；当前不写入基础库或实体关系 |

数值事实和攻略观点分开。例如“腐化使技能费用变为 0，并使打出的技能消耗”是规则；“什么时候开腐化”“是否裸抓”是策略，不应覆盖前者。

## 应覆盖的对象

1. **角色**：名称、初始生命、初始卡组、遗物、资源与特有机制。
2. **卡牌**：稳定 ID、中英文名、别名、角色/颜色、类型、稀有度、目标、基础与升级效果、费用模型、生成/关联牌、关键词。支持 X 费、不可打出、动态数值、多次升级，不能把升级简单压成一个布尔值。
3. **遗物**：稀有度、职业限制、获取渠道、触发时点、次数/计数器、效果和例外。
4. **药水**：稀有度、职业限制、目标、效果、使用条件、与药效增强等机制的关系。
5. **敌人**：分类、所属幕、生命区间、动作、伤害与攻击次数、状态、行动选择规则及进阶变化。
6. **遭遇**：敌人组合、简单/困难池、出现权重与重复限制，不能只存单体怪物。
7. **事件**：出现条件、选项条件、代价、结果、随机分支和进阶差异。
8. **规则**：进阶、地图、商店、营火、奖励、抽牌/弃牌/消耗、洗牌、回合流程、伤害与格挡结算。
9. **状态与资源**：力量、敏捷、虚弱、易伤、脆弱、人工制品、无实体，以及充能球、姿态等。

## 关联设计

基础表可包括：`entities`、`aliases`、`cards`、`card_variants`、`characters`、`relics`、`potions`、`monsters`、`monster_moves`、`encounters`、`events`、`event_options`、`mechanics`、`relations`、`sources`、`evidence`。策略表可在未来另行启用，但不属于当前基础 Wiki。

- `entities` 为不同类别提供稳定身份；接入游戏时另外保存原始内部 ID，中文名称不作主键。
- `relations` 保存有方向、有类型的链接，如属于角色、生成卡牌、施加状态、在遭遇中出现。
- 搭配好坏属于策略关系，带作者、条件和证据，不与“必然触发”的机械关系混为一谈。
- `aliases` 统一简称与译名差异，如腹皮/肚皮 → 全身撞击。
- `evidence` 把来源关联到具体字段、规则或观点，支持冲突记录，避免一个来源链接笼统覆盖整页。
- 所有实体与行为记录区分游戏版本、原版/Mod，敌人数据再区分进阶条件。

示意关系：

```text
重振精神 → 所属角色 → 铁甲战士
重振精神 → 使用机制 → 消耗
重振精神 → 提供效果 → 格挡
消耗 → 触发能力 → 黑暗之拥
消耗 → 触发能力 → 无惧疼痛
```

## 建设顺序与验收

第一步先建立版本、来源和实体清单，再导入四角色与全部基础对象的名称/身份，避免后续链接悬空。详细规则先做战士卡池及通用遗物、药水、状态、事件和一至四幕敌人；其余职业先有完整目录，逐步补详细机制。

未来若启用策略层，再把攻略章节按稳定锚点挂到实体上，保留不同作者的判断；当前阶段不执行此步骤。

首批验收应检查：实体唯一性、中英文/别名解析、升级和进阶分支、链接有效性、来源可追溯、能量图标不漏值、图片数值与版本一致性。总量按已核对清单统计，缺项明确显示为待补，不用模型记忆填满后标为已确认。

Agent 的读取接口可以很简单：按名称/ID 查条目、按字段列对象、读取机制、查看关系。策略原文读取属于未来独立策略层。无需向量数据库，也不必在每次决策时加载整本 Wiki。
