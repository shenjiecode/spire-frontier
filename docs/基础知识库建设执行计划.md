## 3. 采集流程：先查清单，再抓条目

### 3.1 建立来源清单与访问能力探测

1. 检查仓库、现有文档和已有输出，保留用户修改。先写 `source_audit.md`，记录两站可访问入口、栏目、分页/筛选方式、许可、更新时间字段。
2. 英文站先调查 MediaWiki 的 API/导出/页面源码能力。只使用实际发现且成功验证的接口，不猜测接口可用性。可用时优先结构化接口；不可用则解析页面 HTML，浏览器作为动态内容补充。
3. 小黑盒从用户给定首页开始，通过真实分类和条目链接发现文章。已验证的公开目录接口优先保存 JSON 快照；文章正文仍按条目链接请求，静态 HTML 能完整获得内容就直接请求，动态正文才使用浏览器。若接口行为变化，记录阻塞并停止猜测参数。
4. 遵守源站访问限制；遇到验证码、登录限制、403/429，暂停对应采集并记录，不绕过。默认每站串行、请求间隔约 1–2 秒，尊重 `Retry-After`，失败退避，断点续跑。不要为此开通账号、上传本地材料或发布内容。
5. 每个来源保存原始响应或可复查的正文快照、最终 URL、页面标题、访问时间（UTC ISO 8601）、编辑时间/修订号（若有）、SHA-256、抓取器版本。原始页脚、导航和评论不能误作条目正文。

### 3.2 小黑盒逐项操作

1. 按首页所有目标栏目建立目录记录；遍历每个筛选项，合并条目链接并去重。记录 `discovered_from`、栏目、筛选、文章 ID、标题和 URL。
2. 将怪物图鉴中的单体、大小变体、敌人组合区分开；“地精小队”等条目不一定是一种敌人。“能力/Buff”里的状态和同名卡牌分别建实体。
3. 逐条读取标题、正文、基础/升级段落、表格、配图、站内链接、编辑信息。清除“请输入图片描述”等占位词，但原始快照不改动。
4. 图片承载的费用、类型、稀有度或数值，进入待提取字段；OCR 只给候选值，视觉复核后才进入有效字段。不能把卡框颜色单独作为稀有度已确认的证据。
5. 将游戏介绍和机制说明归规则层；职业打法、遗物选择、经验技巧等归策略候选，不自动导入事实表。

### 3.3 英文逐项操作

1. 从已验证的分类入口构造英文目录。检查列表是否分页、懒加载、过滤，分别收集基础与升级信息。
2. 每个页面确认属于 StS1，排除 `Slay_the_Spire_2:` 命名空间和 Mod 页面；仅凭 URL 未带 2 代前缀还不够，必要时看页面游戏标识。
3. 优先读取结构化字段或模板；HTML 文本作为补充。保留能量图标的 `alt/title` 等语义和相关图片。调研已发现直接 `innerText` 会把部分“Gain 能量图标”提取成“Gain .”，不得把这种结果当完整效果。
4. 卡牌记录基础与升级值；敌人逐动作记录伤害、段数、意图、条件、权重及历史动作限制；事件逐选项记录条件、代价和分支。原文没有的数据保留未知。
5. 解析条目间链接为候选关系，识别对应实体后再写正式关系。导航模板里的链接不自动表示机制关系。

### 3.4 合并与差异核对

建立两站清单的并集，再给每个实体标注“双源覆盖 / 中文独有 / 英文独有 / 身份待定”。覆盖不等于内容已核对。

逐字段比较来源，而不是只给整页打一个“已校验”标记。比较费用、伤害、格挡、抽牌、升级、目标、稀有度、条件等；译文语序差异不算规则冲突。发现冲突保存双方值和证据位置，追查版本、进阶、升级、翻译和漏图标等原因。不能默认英文胜出，也不能按来源新旧简单覆盖。

未解决时有效值为未知或明确标记 provisional，同时显示候选值和冲突记录。不允许用模型记忆填充后标成来源事实。

## 4. 中英文名称与身份如何对照

内部主键用项目稳定 ID，例如 `sts1.card.ironclad.body_slam`；这只是项目 ID，不声称是游戏内部 ID。真实 `game_id` 独立保存，没验证则为 null。ID 首次确认后不随译名更换而改变。

名称表至少保存：`entity_id, language, name, name_kind, source_page_id, verification_status`。`name_kind` 区分主显示名、来源原名、游戏本地化名、俗称、旧译名；语言采用 `zh-CN/en` 等明确代码。

对照步骤：

1. 优先使用同一数据源明确提供的双语名或已验证游戏 ID；其次参考页内英文名、对应链接。
2. 没有显式映射时，用类型、角色/颜色、稀有度、费用、效果与升级变化共同形成候选。机器翻译和名字相似只能帮助找候选。
3. 候选经字段核对后标记 `confirmed`；记录匹配依据和证据。不能确认的进入人工审核清单，不强行合并。
4. “打击”“防御”按角色保留不同实体；大小史莱姆等变体独立表示。名称查询可能返回多个结果，必须让调用者指定类别/角色，不能静默选第一个。
5. 卡牌升级通常是同实体下的 variant，不是名称表里独立新卡。“全身撞击+”解析到同一实体的升级变体；特殊重复升级用次数/公式表达。
6. “壁垒”卡牌与“壁垒”状态分开。“战士/铁甲战士”“腹皮/肚皮/全身撞击”等俗称单独入别名，附来源出处；歧义别名允许一对多。

对照清单导出 `name_mapping.csv`：项目 ID、类别、中文名、英文名、角色/变体、两站 URL、映射状态、依据、待办。AI 生成的中文说明标为 `editorial_zh`，不能冒充原站中文原文。

## 5. 数据如何存

### 5.1 单一事实源与目录

SQLite 是正式条目和核对状态的唯一事实源；Markdown 和 JSON/CSV 是生成物，不双向人工同步。原始快照不可覆盖，解析后的候选数据可重建，审核决定必须独立保存并可重放。数据库变更使用 migration 和事务。

```text
data/
  spire.sqlite                 # 正式库；初期作为构建产物，不反复提交二进制 diff
  raw/<source>/<date>/         # 原始快照及 manifest；按大小决定本地/Git LFS
  staging/                    # 解析候选 JSONL；不直接当正式事实
  decisions/                  # 审核、映射、冲突处理决定，可版本控制
  exports/                    # 排序稳定的正式数据 JSONL/CSV，可重建数据库
  assets/                     # 下载后的必要图片，按内容哈希去重
schemas/                      # SQL migrations、字段/枚举规格
scripts/kb/                   # discover/fetch/parse/reconcile/build/validate/export
docs/wiki/
  index.md
  characters/ cards/ relics/ potions/ monsters/
  encounters/ events/ mechanics/ statuses/ keywords/
  sources.md                  # 来源、署名、许可和采集时间
  coverage.md                 # 覆盖率、未解决映射和冲突
  inventory.md                # P2 两站目录发现结果和缺口
docs/基础知识库建设执行计划.md
docs/端口化入门攻略.md
docs/胜利的方程式.md
docs/assets/胜利的方程式/      # 原攻略图片，保持现有路径
reports/                      # 审计、验证、差异报告
tests/kb/                     # 针对边界与解析回归的测试
```

README 写明重建步骤；仅有 `.sqlite` 二进制文件而没有导出、原始依据和构建脚本，不算可交接。抓取缓存和大图片默认不混入代码提交；所有不入 Git 的必需材料明确备份路径与恢复办法。不要提交 Cookie、token 或登录页面。

### 5.2 公共表

| 表 | 关键内容 |
| --- | --- |
| `entities` | 稳定 ID、kind、game、规则集/适用版本、生命周期状态 |
| `names` | 中英文主名、来源原名、俗称、歧义候选、证据 |
| `sources` / `source_pages` | 站点、许可、URL、文章 ID、修订/编辑时间、抓取时间、快照路径、哈希 |
| `claims` | entity/variant、字段路径、候选值 JSON、来源页、段落/表格/图像位置、提取方式、核对状态 |
| `resolutions` | 采用值/采用 claim、冲突处理理由、操作者、时间、适用条件 |
| `relations` | 起点、关系类型、终点、条件、版本、支持证据；提供反向查询 |
| `assets` / `entity_assets` | 原始 URL、哈希、路径、类型、语言、基础/升级用途、许可/署名、关联实体 |
| `strategy_notes` / `strategy_links` | 预留给未来策略层；当前基础库构建时必须为空 |

数据库启用外键。来源缺失和未知字段用 null，不能用 0、空串或空数组伪装“已知没有”。字段状态可用 `unverified / single_source / agreed / conflict / verified_game`；实体映射状态和采集完成状态另设字段。两 Wiki 可能共享上游资料，所以 `agreed` 只表示两页一致，不等于两份独立证据。

专业表保存已经采纳的可查询字段；`claims` 保留候选和来历，二者必须通过同一事务/构建流程保持一致。关键字段都能追溯到 claim，不用一个页级 URL 代替全部字段证据。

### 5.3 各类实体结构

| --- | --- |

| 关键词 `keywords` | 定义、关联机制、适用对象；保留保留/固有/消耗等概念的区别 |
| 机制 `mechanics` | 抽弃消耗、回合结算、伤害/格挡、能量、充能球、姿态、进阶、奖励、商店、地图等；输入/条件/顺序/例外与证据 |

不把整个游戏规则强行编码成可执行引擎。常用数值结构化，复杂规则先存可读说明及带 schema 的条件 JSON。每个 JSON 字段有版本和格式约束，禁止任意自由 JSON 替代全部建模。

进阶变化按字段实际阈值表示，不能只分 A0/A20。基础卡的升级、战斗中的临时费用、永久升级、灼热攻击的多次升级、X 费、不可打出分别处理。伤害字段区分直接伤害、攻击伤害、失去生命和多段攻击。

## 6. 图片要不要存

**建议存必要图片，并本地化；不采集全站所有图片。** 文字和结构化字段应足以回答规则问题，图片用于识别、复核和补充证据。

- 第一优先：卡牌基础/升级图（尤其数字只在图中）、遗物和药水图标、敌人识别图、影响事件选项解释的图、必要的状态图标。
- 第二优先：四角色代表图。测试画风/替代立绘、装饰图、广告、头像、评论图片默认不收；需要时单独扩展。
- 通过合法页面提供的真实资源 URL 下载，不猜图址；记录文章来源、资源 URL、下载时间、SHA-256、MIME、尺寸、用途、语言、版本、署名/许可。按内容哈希去重，不把不同语言/升级图误合并。
- 不为每张图生成缩略图或转格式；展示需要时再生成派生文件，保留原文件。禁止把整页截图当文本知识库替代品。
- OCR/视觉提取记录原图、区域、工具/方法和复核状态；费用和关键数值需与英文结构化信息或其他可核实证据交叉检查。
- 图片不是发布授权。wiki.gg 文本页脚所示 CC BY-SA 4.0 不自动覆盖游戏图片；小黑盒文本及图片许可待核查。许可未知填写 unknown，公开分发时排除未明确可分发的正文/图片，保留来源链接和自写事实概述。不要给整个仓库统一套用某来源的许可。

## 7. 自有 Wiki 页面（策略层暂不接入）

每页使用稳定 ID 对应的固定文件路径，显示“中文名 / English Name”。包含：一句话介绍、属性、基础/升级或进阶差异、机制与例外、相关实体、引用本页的条目、来源及核对状态。当前页面不生成攻略关联章节。

由数据库自动生成普通 Markdown 相对链接，避免依赖 Obsidian 的 `[[链接]]`。同名消歧页列出类别/角色。页面里的字段缺失、冲突、单源状态必须可见，不能只藏在数据库。

明确关系类型，例如 `belongs_to_character / generates_card / applies_status / uses_mechanic / appears_in_encounter / grants_relic`。`synergizes_with` 等策略关系另存，必须有条件与作者出处，不能仅因两页互链就推断存在搭配。

两份现有攻略保持原文和原有图片，暂不纳入基础 Wiki 的来源、字段或关系。`strategy_notes` / `strategy_links` 只作为未来可选扩展保留；启用前需另行确认章节锚点、作者、适用条件和观点冲突，不得由基础库构建脚本自动创建关联。

建议最小查询接口：`get_entity(id_or_name, kind?, character?)`、`list_entities(filters)`、`get_relations(id, direction)`、`get_sources(id, field?)`。策略查询接口仅在未来单独启用策略层后再增加。默认精确名/别名和 SQL 条件查询；可选 SQLite FTS5 关键词全文检索，不引入语义向量。

P1 推荐至少 12 个代表性样本，包含全身撞击（升级可能改变费用但不改效果正文）、一张 X 费牌、灼热攻击、各职业同名打击、壁垒卡与状态、一个遗物、一个药水、一个带进阶变化的敌人、一场多敌人遭遇和一个分支事件。样本实际规则均从来源确认，不把此处列举当现成事实值。

## 9. 验收与质量检查

### 自动检查

- SQLite 外键、唯一键、枚举与 schema 校验；无悬空关系、来源、图片和 Markdown 本地链接。
- 同一输入重复执行不增加重复实体/图片/claim；从导出与审核决定可以重建等价数据库，生成页面内容稳定。
- 双语映射不能跨类别/角色误合并；名称歧义查询明确返回多个候选；所有有效关键字段有来源。
- 所有数字包含单位/语义和适用变体；升级、X 费、不可打出、多次升级、进阶区间均有边界样本。
- 无 StS2/Mod 污染；正文没有残缺能量占位、“请输入图片描述”等提取垃圾；提取错误进入待核查而非悄悄丢弃。
- 图片哈希与 manifest 一致，资源可读取；丢图不能导致已发布字段失去唯一证据。

### 人工/视觉复核

全部身份歧义、数值冲突、OCR 数值和高风险机制必须复核。其余按类别抽样不少于 10% 且每类至少 5 条（不足 5 则全查），对照原页检查；这是质量抽检，不代表未抽到的条目已由人工逐项验证。

用典型查询走通：查“肚皮”到全身撞击及升级；查“打击”得到职业消歧；查一个进阶敌人的完整行动分支；查药水与药效增强规则；从卡牌跳到机制和来源。对精确数值，答案带 variant 和证据。

覆盖报告分别统计：发现条目数、解析成功数、确认身份数、关键字段齐全数、双源可比字段数及一致/冲突数、单源条目、缺图和失败条目。P2 目录报告还要按来源、语言、类别和排除原因统计，并把未匹配的中文/英文目录行单独列出。分母来自经审计的清单及字段定义，不能用任意预设总数或“网页抓完”宣称 100% 完成。

允许最终存在来源本身缺失的事实，但必须列出具体缺口、原因和所需证据。存在未解决冲突的字段不能标“已核实”。最终报告区分“管线完成”“目录覆盖完成”“事实核对完成”。
